# F-506 (dry-run HTML report): normative format specification

This is the normative format spec for the dry-run HTML report. F-506 is P0 per D-04 (the dry-run-first requirement). The report is generated by `abo-core` from a validated plan, with the template baked into the crate. The prototype `_local/gui/06-dryrun-report.html` is the visual and copy reference; where this spec and the prototype disagree, this spec wins (it corrects the prototype's zero-network violation, its mixed duplicate-unit language, and its promise of a complete change list it did not include).

## 1. Purpose and register

The report is the trust ceremony for the early mini-campaign: a family member (tier 2, PRODUCT.md Users) must be able to read it and say what would happen and what would not, before anything moves. Register is plain language throughout (PRODUCT.md Design Principle 1): books, shelves, copies, tidy-up, set aside. Never: operations, ops, dedupe, manifest, quarantine, dashboard. Numbers live inside sentences where possible. The report never brags about its own engineering.

## 2. Self-contained single file (hard constraint)

The report is a single `.html` file that opens correctly from a `file://` path with networking disabled. Zero external requests (FD-11):

- Literata is embedded as a subsetted woff2 data URI, with a system serif fallback stack (`Georgia, "Times New Roman", serif`). The prototype's Google Fonts `<link>`/`preconnect` tags are a prototype-only artifact and never ship.
- No external CSS, JS, images, or fonts. All assets are inlined or data-URI embedded. Any SVG (the masthead mark) is inline.
- A CI grep gate over the template and the app fails the build on any external host or any remote `<link>`/`<script src>`. This gate is a v0.3.0 release-gate item (spec G-5).

## 3. Theme: single light paper theme (distinct from app themes)

The report uses one light "paper" theme with a serif register, by design distinct from the app's Day/Evening themes (FD-28). It does not adopt `data-theme="day"`/`"evening"`; it is a printed-document look: warm paper sheet on a neutral field, serif body, sans-serif for labels/tables/metadata, monospace only where a raw name is shown. Token values follow the prototype's paper palette (`--paper`, `--ink`, `--ink-2`, `--ink-3`, `--border`, `--tint`, `--primary`, `--good`/`--good-bg`, `--warn`/`--warn-bg`). Any informational text must meet WCAG AA 4.5:1 (FD-21); `--ink-3` is restricted to decorative/secondary metadata, not information-bearing body text.

## 4. Required sections, in order

The report contains these sections in this order. Sections that would be empty for a given plan render a plain-language "nothing here" line rather than being omitted.

### 4.1 Masthead and dateline

Inline product mark plus "Audiobook Organizer" wordmark (sans). Title "Dry run report". Dateline: full human date and time ("Friday, July 3, 2026 at 6:14 pm"). Factline (sans, secondary): library location as a friendly name plus shelf layout plus plan and scan identifiers (for example "Shelf layout: author first - Plan 7, scan 4"). The library location on the factline may show the root path (this is a report read by tier 1 for the record, not a primary in-app surface); in-app scanning lines use a friendly name per FD-13.

### 4.2 Lead paragraph

A serif lead that states, in order: this is a preview, nothing has been changed (bold), how many files were read, how many changes were worked out, that they fall into the seven groups, and that any books needing a decision are listed at the end. Sample data rule (FD-27): any specific figure that is illustrative rather than derived from the actual plan is labeled as sample data; a report generated from a real plan uses real counts and is not labeled.

### 4.3 The seven groups at a glance (summary table)

A summary table with one row per user-facing campaign group (FD-26): the seven groups are the sorting piles (staging), loose books, messy names, box sets, bundles, copies, and empty folders. `normalize-series` folds into "messy names" (FD-26); the table shows seven rows, never eight. Columns: what would happen (title + one-line description), changes (count), size, status (a chip: included, or checking/held for the copies group pending the duplicate check). Counts are per group; the copies group counts GROUPS, not pairs or copies (FD-08).

### 4.4 Before/after example tables (per group)

For each group with moves or renames, a before/after table showing a small number of representative examples (the prototype shows 3-6), with a "and N more" line pointing to the complete change-list table at the end. Noise removed in a rename is shown struck through in the "Now" column (the `<s>` treatment). The "After" column uses a subtle separator glyph between path segments, not a raw backslash, in the example tables. Each table header carries a count ("238 changes - showing 6"). Awards (the `^` caret) are explained in the "and N more" line as kept in the report rather than in folder names (ties to F-507 provenance, and to FD-12: no promise of ABS-side tag writes).

### 4.5 Warnings needing a decision (callout)

A highlighted callout listing books that need the user's decision before they are touched (duplicate held until the check finishes; two versions that would land in one folder). Each entry names the book and states plainly that it is not touched until the user decides. If no book needs a decision, this section renders a one-line "Nothing needs a decision" note.

### 4.6 What will not happen (guarantees block)

A guarantees block using the FD-10 canon deletion-guarantee copy. The canonical sentence is used verbatim where the guarantee appears:

> No audiobook is ever deleted. Only empty folders are removed, and every change can be undone.

The block enumerates the reassurances (negated "deleted" is allowed here because this is the enumerating reassurance context, FD-10): duplicate copies move to a "set aside" folder beside the library where they stay until the user empties it; no file contents are edited (books move, folders rename, audio untouched); an undo record is written as changes happen so the whole tidy-up can be reversed; nothing leaves this computer. Primary vocabulary stays "set aside" for the holding area; the word "quarantine" does not appear.

### 4.7 Provenance (F-507)

A provenance section listing every flattened pack/collection and its members, plus award/rank membership (Hugo, Nebula, Top 100, Dune Universe, award markers). This captures provenance that flattening would otherwise destroy (D-14, FD-01). Copy states that pack and award membership is preserved in this report; it does not promise ABS-side collections or tag writes (FD-12). Every flattened pack member appears here (spec AC-25), including members that validation blocked.

### 4.8 Complete change-list table (no row cap)

The complete change list is included in the file (the prototype promised it and omitted it; FD-28 requires it here). It is a single static table with no row cap. Columns: group, book/title, from, to, note. Rows are grouped by campaign group (the seven user-facing groups). There is exactly one row per plan operation (spec AC-21). Because it is a static file, there is no pagination and no virtualization; the file simply contains every row. Raw path detail may appear in the from/to columns of this complete table (it is the of-record appendix, not a primary interactive surface).

### 4.9 Signature line

A closing line (sans, secondary): generated locally by Audiobook Organizer, plan-over-scan identifiers, and a statement that this report is a preview, not a receipt, plus the complete-change-list row count.

## 5. Print rules

The report is printable (`@media print`): drop the page background and sheet chrome, remove the sheet border and shadow, keep headings with their following content (`break-after: avoid` on `h2`), avoid breaking inside table rows and callouts (`break-inside: avoid` on `tr` and `.note`), let long tables break across pages (`break-inside: auto` on `table`). The complete change-list table is expected to span many printed pages and must break cleanly.

## 6. Responsive and accessibility

- Responsive: the sheet has a max width and reduces padding on narrow viewports (the prototype's `@media (max-width:720px)`); tables must not force horizontal body scroll (wide content shrinks or wraps within the sheet).
- Accessibility (PRODUCT.md, FD-21): WCAG AA 4.5:1 for all information-bearing text in the paper theme; status is never color-alone (the summary-table status chips carry a text label, not only a color); the struck-through noise treatment is decorative reinforcement of the "After" column, which already shows the cleaned name, so meaning does not depend on the strikethrough alone.

## 7. Data-unit and labeling rules (cross-cutting)

- Duplicates are counted in GROUPS everywhere in the report (summary chip, headlines, complete table): one book with N identical copies is one group; member files are "copies" (FD-08). Any GB figure states which quantity it measures.
- Sample-data labeling (FD-27): illustrative figures are labeled as sample data; a report generated from a real validated plan uses real derived counts and is not labeled. The prototype's demo arithmetic (1,385 total etc.) is sample data and may be reused only in illustrations, labeled as such.
- Baseline labeling (FD-18): where a figure derives from the stale 2026-03-25 snapshot rather than a fresh scan, it is labeled "2026-03-25 baseline, pending fresh scan".

## 8. Generation and acceptance

The report is generated by `abo-core` from a validated plan (no GUI dependency), so it ships in v0.3.0 (planning) before any GUI exists. Acceptance is covered by the v0.3.0 spec: AC-20 (self-contained, zero network, CI grep gate), AC-21 (all sections present, one complete-change-list row per op), AC-22 (non-engineer read test), AC-23 (FD-10 verbatim block, groups counted, sample data labeled), and AC-26 (provenance section present, no ABS-side promise). Evidence pointers follow docs/internal/test-strategy.md conventions.
