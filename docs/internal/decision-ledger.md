- FD-36 (2026-07-30, orchestrator disposition during v0.6.0, vetoable at the release report) History and undo are pulled into the v0.6.0 (hardening) milestone as P0, alongside F-606 interruption safety. Context: a deep external audit (Codex 5.6, `_local/audit/2026-07-30_audit_codex-56.md`) found that v0.5.0's undo machinery - the self-contained undo file, the inverse-plan builder, and partial rollback from a journal tail - was complete, tested, and UNREACHABLE: the History route was a `ComingSoon` placeholder and no surface called either rollback-preparation command. Rationale: an interruption-safety release that correctly recovers a killed run and then offers the user nowhere to act on it has not delivered the safety story it claims; "undo exists in the engine" is not "undo is available", and user-facing copy already told the user the undo file was saved and that everything could be put back from History. Deliberately out of scope for P0: per-operation drill-down, verification-discrepancy display, and a contiguous-tail picker. Cost: v0.6.0 grows; the alternative was keeping real changes unreachable for longer, which is happening regardless.

- FD-37 (2026-07-30, orchestrator disposition during v0.6.0, vetoable at the release report) Startup reconciliation is gated on `jobs.mode`, and fails closed when the mode is unreadable or when more than one apply job is stranded. Context: the same audit found the F-606 startup sweep queried every `running` apply job without selecting `mode` while the shell unconditionally supplied `RealFs`. Because the shipped frontend pins apply to dry-run, every stranded job in practice was a rehearsal, so a kill during a practice run would probe the user's real library to classify an operation that had only ever touched a `MemFs` - and could report Completed with resume offered purely because the library already happened to match. Nothing was ever written (the reconciler only reads), but the recovery offer was groundless. Migration 0005 added `jobs.mode` expressly so "a dry-run rehearsal is never mistaken for a real apply" during DB-side recovery; this decision makes recovery actually read it. `reconcile_interrupted_job` now takes `ApplyMode` explicitly so the probing path cannot be reached without naming Real at the call site (a property of the signature, not a convention). `jobs.mode` is nullable, so an unreadable mode is a reachable state and resolves to a fail-closed error rather than a default of Real; defaulting to Real for the rows we know least about is the defect itself. Multiple stranded rows break the single-writer invariant and give no way to attribute on-disk state to a job, so they fail closed rather than being swept in id order.

- FD-39 (2026-08-04, orchestrator disposition during v0.6.0, vetoable at the release report) Carrying on after an interruption is satisfied by re-planning from a fresh scan, not by replaying the interrupted job. AC-7 (v0.6.0 hardening) says resume "continues the original job from the reconciled point"; no shipped command does that, and building one is the wrong shape. Context: `apply_start` loads every op of a plan with no already-applied check and opens a new job row; `job_resume` only flips an in-memory pause flag and returns `NothingToResume` once the process has restarted; and `reclaim_stranded_apply_jobs` has already driven the stranded row terminal, releasing the single-writer lock, before any surface could act on it. Rationale: a resume command would replay operations validated against a snapshot the interrupted run itself invalidated, and F-908 already carries a dedicated snapshot-stale re-validation state, which is the codebase's own acknowledgement that replaying a stale plan is a hazard. Re-scanning removes that hazard instead of managing it, because the plan is re-derived from what is actually on disk; the pipeline is already idempotent by re-scan (an already-tidy book yields no operation per `already_tidy_yields_zero_problems`, and an empty ops slice is a legal plan), so changes that landed before the kill do not reappear. AC-7's second sentence, "Neither path bypasses validation", is satisfied more strongly by running the whole validated pipeline than by replaying a frozen one. Scope: only the resume half of AC-7 is restated; the rollback half is unchanged, and `resume_offered` remains load-bearing, because a cross-volume copy killed mid-write leaves a target that exists but may be truncated and a fresh scan would read that as a tidy book. Consequence: P1c (interruption recovery surface) adds no backend command and no migration. Rejected alternatives: a new `apply_resume` with a journal-aware skip, which needs a schema addition to stitch two job ids into one History row and still replays a stale plan; and deferring the startup lock reclaim until the user decides, which reverts startup behaviour merged 2026-07-31 and reintroduces the deadlock the reclaim exists to prevent. Design: `docs/internal/releases/v0.6.0-hardening/design-p1c-interruption-surface.md`.

- FD-40 (2026-08-05, operator decision during the UI round 2 crit pass) Non-audio clutter defaults to being LEFT IN PLACE. `ClutterPolicy`'s defaults for `nfo`, `sfv`, `playlist`, and `weblink` flip from `Quarantine` to `Keep`, joining `ebook` and `cover` which already default to `Keep`. jp: "this should be a setting defaulted to off, so non audio files can optionally stay where they are." Context: the per-type control already exists and ships (`crates/abo-core/src/ruleset.rs`), so this changes only what a fresh install does, not what the ruleset can express. Rationale: setting aside a `.nfo` file next to a book is the tool touching something the user did not ask about, in a product whose whole promise is that it does not surprise you; a user who wants those files gone can turn it on, and a user who does not should never have to discover the setting to prevent it. Consequence: the default ruleset drives plan output, so golden fixtures and any test asserting clutter set-aside move with this. Small but engine-touching, not a doc change. Superseding note: `FD-31`'s clutter-group inheritance is unaffected; it governs which user-facing group a clutter operation joins WHEN one is emitted, not whether one is emitted.

- FD-41 (2026-08-05, orchestrator disposition during the UI round 2 crit pass, vetoable) Library scanning is EVENT-TRIGGERED and the app never watches the filesystem. Five triggers and no others: manual request, entering the tidy-up flow, undo completion, tidy-up completion, and app start when the stored scan is older than a threshold. Context: jp asked whether the app re-scans when a tidy-up starts (it does not) and proposed triggers over watching. Rationale: a filesystem watcher is a background process running for the life of the app, a source of bugs, and a per-platform behaviour difference, all to cover a risk that three of the five triggers already cover at the moment it matters. The dangerous window is not "the library changed" but "the library changed and you are about to act on a plan that predates it", which is precisely the entering-tidy-up trigger. Recorded as `F-609` in the v0.6.0 spec with `AC-42` to `AC-46`. Also records that the passive browse-time notice drawn in a round 1 mockup ("4 new files appeared") was never built and is deferred as `F-1109`; it was an invented capability, not a descoped one.
