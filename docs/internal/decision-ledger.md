- FD-39 (2026-08-04, orchestrator disposition during v0.6.0, vetoable at the release report) Carrying on after an interruption is satisfied by re-planning from a fresh scan, not by replaying the interrupted job. AC-7 (v0.6.0 hardening) says resume "continues the original job from the reconciled point"; no shipped command does that, and building one is the wrong shape. Context: `apply_start` loads every op of a plan with no already-applied check and opens a new job row; `job_resume` only flips an in-memory pause flag and returns `NothingToResume` once the process has restarted; and `reclaim_stranded_apply_jobs` has already driven the stranded row terminal, releasing the single-writer lock, before any surface could act on it. Rationale: a resume command would replay operations validated against a snapshot the interrupted run itself invalidated, and F-908 already carries a dedicated snapshot-stale re-validation state, which is the codebase's own acknowledgement that replaying a stale plan is a hazard. Re-scanning removes that hazard instead of managing it, because the plan is re-derived from what is actually on disk; the pipeline is already idempotent by re-scan (an already-tidy book yields no operation per `already_tidy_yields_zero_problems`, and an empty ops slice is a legal plan), so changes that landed before the kill do not reappear. AC-7's second sentence, "Neither path bypasses validation", is satisfied more strongly by running the whole validated pipeline than by replaying a frozen one. Scope: only the resume half of AC-7 is restated; the rollback half is unchanged, and `resume_offered` remains load-bearing, because a cross-volume copy killed mid-write leaves a target that exists but may be truncated and a fresh scan would read that as a tidy book. Consequence: P1c (interruption recovery surface) adds no backend command and no migration. Rejected alternatives: a new `apply_resume` with a journal-aware skip, which needs a schema addition to stitch two job ids into one History row and still replays a stale plan; and deferring the startup lock reclaim until the user decides, which reverts startup behaviour merged 2026-07-31 and reintroduces the deadlock the reclaim exists to prevent. Design: `docs/internal/releases/v0.6.0-hardening/design-p1c-interruption-surface.md`.

- FD-40 (2026-08-05, operator decision during the UI round 2 crit pass) Non-audio clutter defaults to being LEFT IN PLACE. `ClutterPolicy`'s defaults for `nfo`, `sfv`, `playlist`, and `weblink` flip from `Quarantine` to `Keep`, joining `ebook` and `cover` which already default to `Keep`. jp: "this should be a setting defaulted to off, so non audio files can optionally stay where they are." Context: the per-type control already exists and ships (`crates/abo-core/src/ruleset.rs`), so this changes only what a fresh install does, not what the ruleset can express. Rationale, in jp's words (2026-08-05): "people often store accompanying resources alongside audio books... while that doesn't matter for audiobookshelf... this is still just a file structure." That is the sharper form of the argument and it is worth preserving verbatim: the folder is not only an Audiobookshelf feed, it is also the user's own filing system, and companion material (liner notes, PDFs, cue sheets, cover scans, series artwork) is often there BY INTENT. Moving it breaks a structure someone built deliberately, in order to satisfy a consumer that does not care either way. The weaker general form still holds: setting aside a `.nfo` is the tool touching something the user did not ask about, in a product whose whole promise is that it does not surprise you; a user who wants those files gone can turn it on, and a user who does not should never have to discover the setting to prevent it. Consequence: the default ruleset drives plan output, so golden fixtures and any test asserting clutter set-aside move with this. Small but engine-touching, not a doc change. Superseding note: `FD-31`'s clutter-group inheritance is unaffected; it governs which user-facing group a clutter operation joins WHEN one is emitted, not whether one is emitted. **Regression this flip exposed, found by an adversarial Codex review before merge:** `pass_split_multi_book` decided a folder had been emptied by counting only its AUDIO children, so a multi-book folder holding a now-kept `.nfo` was still scheduled for `rmdir-empty`. The executor refuses to remove a non-empty directory and turns that into a HALT, landing AFTER the book moves in the same run had already been applied - a half-finished tidy-up on the most ordinary layout there is, on the DEFAULT settings. Neither the unit tests nor the committed plan golden caught it, because no fixture had a multi-book folder that was both emptied and held clutter. Fixed by re-checking every direct child at emission time and biasing conservative: an unprovable child means the folder is kept, since a stray empty folder costs nothing and a halted run costs a lot. The lesson generalises beyond this decision: **a default that changes what the planner emits can invalidate an assumption held somewhere else in the pipeline entirely**, and the place to look is wherever one pass records a conclusion for a later pass to act on.

- FD-42 (2026-08-05, operator decision during the UI round 2 crit pass) "Set Aside" is renamed to "Archive", and the on-disk folder is named "Audiobook Archive". Consequences: supersedes the naming half of `FD-31` (the on-disk name was "Set Aside") and the naming in `FD-34` (placement is unchanged: still a sibling, still `<job-id>` segmented). `QUARANTINE_DIRNAME` in `crates/abo-core/src/plan/builder.rs` is the single constant. Three independent verifications, each read from the code rather than assumed. **First, undo never reconstructs a path.** Inverse ops are built by swapping the FROZEN `plan_ops` source and target, which are absolute and recorded at apply time; `exec::rollback::resolve_set_aside_root`'s own doc states it is "only used for the inverse plan's F-404 scope check... this root only ever affects a defensive out-of-scope verdict, never the paths". **Second, teardown already survives a changed root.** `exec::rollback::effective_set_aside_root` derives the boundary from the per-job folder's own `mkdir` target in the manifest, which was built for the P4 settings race and covers a renamed default unchanged. **Third, teardown ops are not scope-checked at all.** The `OutOfScopeTarget` guard in `plan::validate` sits inside `if creates_target(&op.kind)`, and `creates_target` is `move | rename | mkdir | quarantine`; teardown is `rmdir-empty`, which is excluded, and its `target_path` is empty besides. **The remaining consequence is cosmetic and it is currently vacuous: no install can hold a `Set Aside` folder this app created**, because real applies have never been reachable (`AppShell.tsx` hardcodes `applyStart(planId, "dry-run")`, and a dry run executes against `MemFs`, touching no real filesystem).
